# 中文 RAG eval 满分之路：用 LLM-as-judge 把 RAG 质量从 6.1 量化优化到 8.0

> [Spring AI 中文踩坑系列] 第五篇，也是**方法论篇**。前几篇讲"怎么改 RAG"，这篇讲"**怎么知道改好了**"。做 RAG 最怕的是凭感觉调参——换个 embedding、加个 reranker，肉眼看答案"好像变好了"，但到底是真好了还是碰巧这题对了？不知道。本文给出一套 **LLM-as-judge 量化评测**方法，把 RAG 质量变成可对比的分数，并用它把我的项目从 6.1 分一路优化到 8.0 满分，每一步都零回归。

---

## 一、痛点：没有 eval 的 RAG 优化是黑盒

RAG 优化有个典型死循环：

1. 你觉得答案不够好；
2. 你改了检索（换个分词、加个 reranker）；
3. 跑两题肉眼看，"好像好了"；
4. 上线发现别的题变差了；
5. 回到第 1 步。

**根因**：没有量化。你不知道改动到底是 +0.5 还是 -0.3，也不知道是不是用 A 题的改善换来了 B 题的退化。

解法只有一个：**搭一个可重复运行的评测基准，每次改动前后都跑一遍，用分数说话。**

---

## 二、方案：LLM-as-judge 评测

核心思想：**用一个强模型（裁判）按固定标准，给你的 RAG 系统的答案打分**。

不需要人工标答，只需要：
1. 一套**黄金题集**（问题 + 参考要点）；
2. 一份**评分标准**（rubric）；
3. 一个**裁判模型**（我用 GLM-5.2）；
4. 一个**脚本**自动跑：拿题 → 调你的 RAG 拿答案 → 裁判打分 → 出报告。

我的项目里这套东西放在 `eval/` 目录：

| 文件 | 作用 |
|---|---|
| `golden-qa.jsonl` | 10 题 ground truth（问题 + 参考要点） |
| `rubric.md` | 4 维评分标准，各 0-2 分，满分 8 |
| `judge.py` | 主脚本：调 RAG 拿答案 → GLM 按 rubric 打分 → 输出 `results-标签.json` |
| `compare.py` | 读两个 results 对比，输出胜率表 |

---

## 三、rubric 设计：4 维评分，接地性惩罚幻觉

这是整套方法论的灵魂。评分不能只看"答得对不对"，要分维度，每个维度都有清晰判据：

| 维度 | 2 分 | 1 分 | 0 分 |
|---|---|---|---|
| **准确性 accuracy** | 事实完全正确，无编造 | 大体正确，有轻微瑕疵 | 关键事实错误或编造 |
| **相关性 relevance** | 完全切题，直击问题 | 部分跑题 | 完全答非所问 |
| **完整性 completeness** | 覆盖参考要点全部 | 覆盖部分要点 | 遗漏核心要点 |
| **接地性 grounding** | 答案可由语料支撑，无外部臆造 | 混入少量语料外内容 | 大量臆造，与语料无关 |

每维 0-2，满分 8。**为什么专门设"接地性（grounding）"这一维？** 因为 RAG 最大的失败模式不是答错，而是**幻觉**——模型用参数知识编一个语料里没有的答案，听起来头头是道但根本不是从你的知识库来的。grounding 维度专门惩罚这种"看起来对但其实没依据"的答案。

还有一个设计原则特别重要，写在 rubric 里：

> **鼓励诚实"不知道"优于编造**（接地性维度惩罚幻觉）。

也就是说，如果系统说"知识库里没有相关信息，我不知道"，接地性给高分；如果它瞎编一个，接地性给 0。这引导 RAG 往"诚实"而不是"自信地胡说"的方向优化。

## 四、judge.py：仅标准库、温度 0、强制 JSON、降级重试

裁判脚本有几个工程细节值得说，全部用 Python **标准库**实现（`urllib`，零依赖，随便哪台机器能跑）：

### 1. 裁判温度设 0，保证可复现

```python
base = {"model": model, "messages": [...], "temperature": 0.0}
```

裁判打分必须**可复现**——同样的答案，今天打 7 分明天打 5 分就没法对比。温度设 0 让裁判输出稳定（虽然不是 100% 确定，但已经足够一致）。

### 2. 强制 JSON 输出 + 降级重试

```python
def judge_one(judge_url, model, tok, q, exp, ans, timeout=60):
    prompt = RUBRIC.format(q=q, exp=exp, ans=ans)
    def call(extra):
        p = dict(base, **extra)
        b = http_json(judge_url, p, headers, timeout)
        t = b["choices"][0]["message"]["content"]
        m = re.search(r"\{.*\}", t, re.S)   # 正则兜底提取 JSON
        return (json.loads(m.group(0)) if m else None), ...

    # 先尝试 response_format=json_object 强制结构化
    sc, err = call({"response_format": {"type": "json_object"}})
    if sc: return sc, None
    # 失败降级：去掉 response_format 重试
    sc, err2 = call({})
    return sc, err2
```

两层保险：
- 先用 OpenAI 兼容的 `response_format: json_object` 让模型直接输出结构化 JSON；
- 如果模型/端点不支持，降级去掉这个参数重试，并用正则 `\{.*\}` 从自由文本里兜底抠出 JSON。

### 3. 分数必须可解释

rubric 强制裁判输出 `reason` 字段说明扣分点：

```json
{"accuracy":2,"relevance":2,"completeness":1,"grounding":2,"reason":"未点出'不要编造'这一关键约束"}
```

**不可解释的分数没用**——你只知道"这题扣了 1 分"，不知道为什么，就没法优化。reason 让每个扣分都能追溯到具体原因。

### 4. 黄金题集设计原则

> 10 题 ground truth，**基于已灌入的设计文档，确保可检索**。

这是个关键约束：题目的答案**必须在你已经灌进向量库的语料里**。否则你测的不是"检索+生成"能力，而是"模型自己的知识"，那 eval 就失真了。

## 五、实战：方案链 6.1 → 7.8 → 7.8 → 8.0，全程零回归

有了 eval 基准，优化就变成了"改 → 跑 eval → 看分数"的闭环。我的真实优化路径：

| 方案 | 改动 | 平均分 | 满分题数 |
|---|---|---|---|
| **baseline** | 初始（向量检索 + nomic-embed-text） | **6.1 / 8** | — |
| **chinese-tokenizer** | 加 jieba 中文分词修 BM25 召回 | **7.8 / 8** | — |
| **reranker-on** | 开 TEI reranker 精排 | **7.8 / 8** | — |
| **bge-m3** | 换 bge-m3 1024d 中文 embedding | **8.0 / 8** | **10/10** |

（以上每个数字都是 `results-*.json` 里的 `avg_score`，GLM-5.2 裁判，10 题。）

### 关键拐点 1：baseline 6.1 → 7.8（中文分词）

baseline 只有 6.1 分，跑出来发现 q02、q06 这种题**直接 0 召回**（RAG 报"不知道"或乱答）。定位到根因就是第三篇讲的——**RediSearch 默认按空格切词，中文整句成一个 token，BM25 召回为 0**。

加 jieba 分词修了之后，这两题召回恢复，分数直接跳到 7.8。**+1.7 分，全靠修一个分词 bug。**

### 关键拐点 2：7.8 → 8.0（bge-m3 中文 embedding）

reranker 开了之后还是 7.8（没涨，因为瓶颈不在排序而在 embedding 召回质量）。换成 bge-m3（1024 维，中文优化）后，达到 **8.0 满分，10 题全满分**。

### 全程零回归

每一步都用 `compare.py` 对比前后两个 results，**确认提升的同时没有别的题退化**。这是 eval 最大的价值——它让"零回归"从口号变成可验证的事实。

## 六、对照评测：公平对比两个系统

这套 eval 还能做**跨系统对照**。我用同语料、同题集、同裁判，对比了我的 ka 和另一个开源系统 WeKnora：

| 系统 | 平均分 | 满分题数 | 平均延迟 |
|---|---|---|---|
| **knowledge-assistant**（bge-m3 + reranker + GLM-5.2） | **8.00 / 8** | 10/10 | 11.5s |
| **WeKnora**（nomic-embed-text + qwen3.6:35b，无 rerank） | **7.80 / 8** | 8/10 | 23.0s |

逐题明细揭示了一个**反直觉**的结论：

- WeKnora 丢的两分（q02、q09）**都不是检索失败**（召回 `refs=10` 都正常）；
- q02：WeKnora 正确答出 Ollama，但 LLM 画蛇添足补了语料里没有的"通过 Spring AI 框架调用"→ **接地性 2→1**；
- q09：WeKnora 正确答出"诚实回答不知道"，但没点出"不要编造"→ **完整性 2→1**。

**也就是说，WeKnora 的短板在 LLM 生成层（qwen3.6:35b），不在检索层。** 如果它换 GLM-5.2 生成，这两分大概率能拿回，追平 8.0。

这个结论**只有靠 LLM-as-judge + 逐题 reason 才能得出**——肉眼看总分 7.8 vs 8.0，你只会以为 WeKnora 检索差，其实它检索很扎实（无 rerank 都 7.8），差在 LLM 选型。基于这个发现，我判断"不需要集成 WeKnora"——ka 已经更准更快。

> 💡 **这就是 eval 的终极价值：把模糊的"谁更好"变成可追溯的"差在哪、为什么差、值不值得改"。**

## 七、避坑速查表

| 坑 | 现象 | 根因 | 修复 |
|---|---|---|---|
| 凭感觉调 RAG 参数 | 改了不知道好坏 | 没有量化 | 搭 LLM-as-judge eval |
| 裁判打分忽高忽低 | 不可复现 | 温度 > 0 | 裁判温度设 0 |
| 分数不可解释 | 知道扣分不知为何 | 没要 reason | rubric 强制 reason 字段 |
| 题目答案模型自己会 | eval 失真 | 题不基于灌入语料 | 黄金集答案必须在向量库语料里 |
| RAG 幻觉拿高分 | 编造答案得高分 | 只看准确性 | 加 grounding 维度惩罚臆造 |
| 改动后别题退化 | 隐性回归 | 没全量对比 | compare.py 对比前后 results |
| 模型不输出 JSON | 解析失败 | 端点不支持 response_format | 正则兜底 + 去参重试 |
| 总分相近看不出差异 | 以为检索差 | 没看逐题 | 看逐题 reason 定位丢分层 |

## 写在最后

这篇没有"代码坑"，但可能是整个系列**最值钱的一篇**。因为前几篇的每一个改动——加 reranker、修中文分词、换 embedding——**都是靠这套 eval 验证了"确实有效且零回归"才敢落地的**。没有 eval，那些改动只是赌博。

一句话总结：**RAG 优化必须配 eval。LLM-as-judge（强裁判 + 4 维 rubric + 可解释 reason + 零回归对比）是最轻量的方案。把质量变成分数，优化才有方向。**
